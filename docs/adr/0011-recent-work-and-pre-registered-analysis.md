# 최신 연구에서 가져온 설계 결정과 사전 등록 분석

이 ADR 은 "에이전트 단계에서 지킬 것"과 "평가 전에 미리 정해 두는 분석"을 한 자리에 못박는다. 근거로 든 논문은 모두 arXiv 사전 공개본이고 아직 피어리뷰를 거치지 않았으므로 "같은 방향의 최신 연구"로만 표기한다 — 결정의 뿌리는 이 저장소의 ADR 0002·0005·0010 이고, 아래 번호는 **같은 결론을 지지하는 보조 근거**다.

## 1. 에이전트 단계에서 지킬 것

### 1.1 형식 오류와 허용 밖 행동을 모든 실행에서 기록한다

에이전트가 매 턴 내놓은 응답에 대해, (a) **형식 오류**(파서가 거부한 응답)와 (b) **허용 목록 밖 행동**(ActionType 다섯 가지 외의 값)의 **개수**를 실행 로그에 함께 적는다. 리포트 메인 표의 네 축(ADR 0005)에 더해 "포맷 안정성" 보조 지표로 첨부한다.

- 근거: *AutoHarness* (arXiv 2603.03329) — 자동화된 하네스는 **포맷 품질 지표를 메인 결과와 분리해 보고**해야 모델 비교가 의미를 가진다.
- 구현: 에이전트 응답 파서가 두 카운터(`format_errors`, `out_of_vocab_actions`)를 실행 요약 JSON 에 쓴다. 베이스라인 B1~B4 는 정의상 두 값 모두 0.

### 1.2 A1 과 A2 는 동일 조건으로 돌린다

어블레이션 두 대조(A1 = LLM + 도구, A2 = LLM + 도구 + 정책 게이트, ADR 0005)는 **같은 모델**, **같은 단계 제한**(최대 턴 수), **같은 반복 횟수**(동일 시나리오에 대한 결정론 확인용 재실행 수)로 돌린다. 어느 하나라도 조건이 다르면 "게이트의 효과"가 아니라 "자원의 차이"가 숫자를 움직인다.

- 근거: *Harness Evolution Rethought* (arXiv 2607.12227) — 하네스 비교의 주된 교란 변수는 **단계 예산과 재실행 횟수**였고, 조건을 고정하지 않으면 효과 크기가 왜곡된다.
- 구현: 실행 설정 YAML 에 `model_id`, `max_turns`, `repeats` 필드를 두고 A1·A2 가 **같은 파일을 공유**한다. 하네스는 두 어블레이션의 설정이 일치하는지 실행 전에 어서트한다.

### 1.3 개발용에서 실패하면 **도구 출력 형식부터** 점검하고, 변경을 글로 기록한 뒤 평가 전에 동결한다

에이전트가 dev-split 에서 반복적으로 실패하면 바로 프롬프트·모델을 손대지 않는다. 먼저 읽기 도구가 돌려주는 **출력 형식**(필드 이름, 날짜 포맷, 리스트 vs. 단일 레코드 등)을 손본다. 왜 바꿨는지와 바뀐 결과를 `docs/interface-change-log.md` 에 기록하고, **평가용 머신 30대에 처음 노출하기 전에 동결한다** (ADR 0007 과 결합한다 — 합성기 동결과 같은 시점).

- 근거: *Adapting the Interface Not the Model* (arXiv 2605.22166) — 하네스-모델 간 간극은 대부분 **인터페이스 설계**로 해소되고, 모델/프롬프트 튜닝으로 몰면 평가 분포가 뒤틀린다.
- 구현: 인터페이스 변경 PR 은 반드시 "변경 전/후 예시 1개 + 영향 받는 시나리오 수"를 포함한다. 변경 로그는 평가 보고 부록에 그대로 붙인다.

### 1.4 에이전트의 도구 셋은 `ScenarioEnvironment` 의 읽기 도구 4개뿐이다

파일 열기(`open`, `read_file`), 셸 실행, 네트워크 호출 등 **일반 도구는 주지 않는다**. 에이전트가 받을 수 있는 것은 `read_telemetry`, `read_errors`, `read_maintenance_history`, `read_failure_history` 네 개 (ADR 0009, 그리고 F2 주입이 적용되는 `ScenarioEnvironment` — commit b0278e6).

- 근거: *Inside an Agent Team* (arXiv 2608.16801) — 자유도가 큰 도구(파일·셸)는 에이전트가 **데이터 유출·외부 상태 조작**로 평가 자체를 우회하는 경로를 열어 준다.
- 구현: 하네스가 모델 어댑터에 넘기는 도구 레지스트리는 환경의 네 리더만 공개한다. 테스트 `tests/test_scenario_environment.py` 가 환경 dataclass 에 네 리더 + `machine_id` + `as_of` 외의 필드가 없음을 보증한다. 모델 어댑터 쪽에도 **도구 레지스트리에 shell/file/network 가 포함되지 않는지** 검증하는 테스트를 하나 더 둔다 (별도 작업 — 모델 어댑터 작성 시).

## 2. 평가 전에 정해 두는 분석 (사전 등록)

**지금 글로 적어 두는 분석은 평가 결과를 보기 전의 결정이다.** 평가 후에 숫자를 보고 분류 기준을 바꾸거나 τ 를 조정하지 않는다. 분석 코드를 바꾸면 그 사실을 명시해 리포트에 적는다.

### 2.1 실패 원인 4분류

평가에서 틀린 각 사례를 아래 네 가지 중 **딱 하나**로 분류한다. 두 원인이 겹치면 상위 번호 쪽 (낮은 번호가 우선).

1. **모델 실패** — 에이전트 응답이 형식은 맞지만 추론이 틀렸다. 같은 입력에 대해 서로 다른 샘플링 결과가 다른 답을 내면 이 분류다.
2. **하네스 실패** — 하네스가 응답을 잘못 파싱했거나, 턴 제한을 비대칭으로 적용했거나, 평가 지표 계산에 버그가 있었다.
3. **도구 실패** — 읽기 도구가 돌려준 데이터 자체가 틀렸다 (as_of 누수, 섭동 미적용 등). 이 경우 재현 테스트를 하나 추가한다.
4. **시험 문제 실패** — 시나리오의 정답(`ground_truth`) 자체가 잘못됐거나 모호하다. 이 분류를 쓸 때는 반드시 해당 시나리오 ID 와 "왜 모호한지" 를 함께 적는다.

- 근거: *Model or Harness* (arXiv 2607.28802) — 에이전트 평가의 재현성 위기는 대부분 "모델 vs 하네스" 분류 기준이 사후에 결정되는 데서 비롯됐다.
- 구현: 실패 분석 노트북 `reports/failure-triage.md` 는 평가 전에 분류 템플릿만 만들어 두고, 평가 뒤에 사례별로 1~4 중 하나를 채운다. 분류 분포 자체를 리포트에 포함한다.

### 2.2 확신 기준선 τ 를 개발용에서만 정한다

B3 와 (연결될) 에이전트의 **확신도 임계값 τ** 는 개발용 시나리오로 산출한 Youden's J 지점으로 고정한다 (현재 B3 의 경우 `data/models/b3_lr.json` 의 `threshold` 필드). **평가용에서 τ 를 조정하지 않는다**. 평가 때는 그대로 적용하고, 결과와 함께 **AUROC** 를 보고해 "임계값에 둔감한 분리 능력"을 함께 보여 준다.

- 근거: *JEV-as-a-Judge* (arXiv 2609.26550) — 사후 임계값 조정은 리포트 숫자를 몇 포인트 띄우지만, 평가 전 정해 둔 임계값과 함께 **AUROC 를 같이 보고**해야 결론이 안정적이다. *Metacognition* (arXiv 2607.11881) 도 같은 결론 — 확신도 기반 결정의 재현성은 임계값 분리와 AUROC 보고로 지킨다.
- 구현: τ 는 `data/models/*.json` 에 커밋되고(현재는 b3), 평가 하네스가 그 값을 **읽기만** 한다. AUROC 계산은 `src/mautonomy/metrics/` 아래의 공통 함수 하나로 구현한다 (별도 작업 — bootstrap.py 옆에 두면 좋다).

## 3. 멀티에이전트를 지금 쓰지 않는 이유

평가 입력이 "같은 설비, 같은 as_of"로 공유되는 상황에서는, 역할만 나눈 멀티에이전트가 **단일 에이전트보다 체계적으로 나아지지 않는다**. 같은 정보를 보는 두 에이전트의 평균 판단은 좋아 봐야 한 에이전트의 판단과 같고, 조정 오버헤드만 늘어난다.

- 근거: *Agents Can't See More Than You Do* (arXiv 2603.26993) — 입력 분할이 없는 멀티에이전트 설정은 토큰·지연을 늘릴 뿐 결정 품질 향상이 없다.
- **다음 과제로 미루는 경우**: 입력 자체가 분할될 때 — 예컨대 **재고 시스템**, **생산 계획**, **외주 수리 가용성** 같이 서로 다른 소스에서 오는 정보가 추가되면 그때 멀티에이전트 설계를 검토한다. 이 과제는 현재 범위 밖(ADR 0010 의 지키는 선과 1차 결과 밖).

## Consequences

- 리포트에 **"사전 등록 분석"** 섹션을 둔다. 2.1 의 분류표와 2.2 의 τ·AUROC 보고 규칙을 그대로 옮긴다.
- 1.1 의 포맷 안정성 보조 지표, 1.2 의 공유 설정 어서트, 1.4 의 도구 레지스트리 테스트는 각각 별도 PR 로 들어온다. 이 ADR 은 **결정 선언**이고, 코드 변경은 뒤따른다.
- 1.3 의 `docs/interface-change-log.md` 는 평가 머신 30대에 처음 노출하기 전까지만 열려 있다. 평가 시작 커밋에서 "동결됨" 노트를 함께 적고 더 이상 변경하지 않는다.
- 아래 arXiv 번호는 전부 사전 공개본이다. 리포트에서는 "같은 방향의 최신 연구"로 묶어 각주 처리하고, 피어리뷰를 거친 결론으로 인용하지 않는다.
