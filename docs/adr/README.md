# ADR 목록 (쉽게 읽는 색인)

## 공장 비유로 보면

이 저장소는 "로봇 정비공을 더 똑똑하게 만드는 공장"이 아니라 "로봇 정비공이 어디까지 혼자 결정해도 괜찮은지를 재는 **검사 라인**"이다. 검사에 쓰는 재료는 진짜 설비 센서 기록 조각이지만, 거기에 일부러 **함정(일부러 틀리게 보이도록 섞은 신호)** 을 심어 로봇을 시험한다. 공정하게 재려고 세 가지 선을 긋는다: ① 설비 정지는 반드시 사람이 결정한다, ② 평가용 설비 30대는 검사가 끝날 때까지 로봇에게 보여주지 않는다, ③ 받아 쓴 데이터를 밖으로 다시 뿌리지 않는다. 검사 결과는 네 각도로 나온다 — **비용표**(틀리면 얼마짜리 손해인가), **쌍 맞히기**(비슷한 두 상황에서 각각 정답을 냈나), **사람 호출 품질**(필요할 때만 사람을 불렀나), **적시 비율**(너무 이르지도 늦지도 않게 조치했나).

---

## 결정 하나씩

### 0001 — Azure PdM 데이터는 저장소에 올리지 않는다
- **무엇을 정했나**: 마이크로소프트의 설비 샘플 데이터(CSV)를 깃허브에 올리지 않고, 각자 Kaggle에서 받아 자기 컴퓨터에만 둔다.
- **왜 그렇게 정했나**: 그 데이터의 재배포(남에게 다시 나눠주는 것) 허락이 명확하지 않아서다.
- **대신 버린 방법**: 저장소에 CSV를 그대로 커밋해 재현을 간단하게 만드는 길.

### 0002 — 중심은 에이전트가 아니라 검사 라인(평가 하네스)
- **무엇을 정했나**: 잘 작동하는 로봇을 만드는 대신, 로봇의 **자율성 판단**(언제 혼자 할지·사람을 부를지·아무것도 안 할지)을 재는 시험장을 만든다.
- **왜 그렇게 정했나**: 비슷한 성능 비교(PHMForge)는 이미 있고, 우리는 "안전·자율성" 축으로 좁혀야 솔로 일주일에 이긴다.
- **대신 버린 방법**: 모델·프롬프트를 다듬어 숫자를 올리는 "에이전트 중심" 접근.

### 0003 — 하드케이스는 실제 데이터 구간에 함정을 심어 만든다
- **무엇을 정했나**: 어려운 평가 문제는 실제 Azure 설비 기록 조각 위에, 패밀리별로 섭동(일부러 넣은 함정)을 코드로 주입해 만든다.
- **왜 그렇게 정했나**: 마이크로소프트가 데이터 생성 공식을 공개한 적이 없고, 처음부터 만든 데이터는 "가짜 같다"는 평을 받기 쉬워서다.
- **대신 버린 방법**: 데이터에서 생성 규칙을 추측해 역추적하거나, 바닥부터 가상 신호를 만드는 길.

### 0004 — 정책 규칙은 파이썬 함수 묶음으로 쓴다
- **무엇을 정했나**: 금지·승인·에스컬레이션(사람에게 넘기는 규칙)을 파이썬 함수들의 레지스트리(목록 묶음) 하나로 쓴다.
- **왜 그렇게 정했나**: OPA/Rego(산업 표준 정책 전용 언어)는 솔로 일주일에는 공부 비용이 크고, 우리 규칙은 "상태"가 없어 상태기계가 과잉이다.
- **대신 버린 방법**: OPA/Rego 로 쓰기, YAML + 상태기계로 쓰기.

### 0005 — 메인 지표는 네 각도로 함께 본다
- **무엇을 정했나**: **비용 총합**, **쌍 정확도**(쌍 두 문제 다 맞혀야 1점), **Ask-F1**(사람 호출의 정확·재현을 묶은 점수), **적시 비율** — 네 지표에 신뢰구간을 붙여 보고한다.
- **왜 그렇게 정했나**: 정확도 하나로는 "언제 안 할지"의 판단을 공정하게 못 잰다.
- **대신 버린 방법**: 비용 하나만 보기, 정확도 하나만 보기, PHMForge 식 과제 성공률만 쓰기.

### 0006 — 고장은 세 시점으로 라벨링하고, 정답 구간은 가장 이른 "이상 시작"부터 센다
- **무엇을 정했나**: 각 고장을 **이상 시작**(변화가 시작된 때) → **처음 드러남**(센서로 보이는 때) → **되돌릴 수 없는 시점** 세 점으로 적고, 그 중 "이상 시작 ~ 되돌릴 수 없는 시점" 사이에 조치하면 정답으로 본다.
- **왜 그렇게 정했나**: 예지정비(미리 고치는 것)의 핵심 가치는 **에러 코드가 뜨기 전**에 알아채는 것이다.
- **대신 버린 방법**: "처음 드러남"부터 세기(그러면 임계값 모니터링과 다를 게 없다), 조치·유보 이진 라벨.

### 0007 — 설비는 모델별 섞어 70/30, 평가 문제 만든 뒤 합성기는 손 안 댄다
- **무엇을 정했나**: 설비 100대를 모델(기종)별로 섞어 70대(개발용)/30대(평가용)로 나누고, 평가용 하드케이스를 생성한 뒤에는 합성기 코드를 수정하지 않는다.
- **왜 그렇게 정했나**: 평가용 설비를 개발 중에 보면 숫자가 거짓이 되고, 결과가 마음에 안 들어 합성기를 고치는 유혹을 막아야 한다.
- **대신 버린 방법**: 번호 순서로 자르기(기종 분포가 치우친다), 합성기를 평가 중에도 자유 수정하기.

### 0008 — 자동 테스트(CI)는 완전 합성 스모크만, 가짜 모델로 돌린다
- **무엇을 정했나**: 깃허브 액션에서는 Azure 데이터를 쓰지 않는 완전 합성 예시 몇 개와, 정해진 답만 내는 **가짜(stub) 모델** 로 끝에서 끝까지 스모크 테스트(가장 얕은 통과 확인)만 돌린다.
- **왜 그렇게 정했나**: Azure 데이터는 커밋 못 하고(ADR 0001), MLX(맥 전용 로컬 추론 라이브러리)는 리눅스 러너에서 안 돈다.
- **대신 버린 방법**: CI 에서 전체 평가 돌리기, VCR 캐시(저장된 모델 응답 재생) 를 커밋하기.

### 0009 — 조회 도구는 "지금 시점" 이후 기록을 코드에서 잘라낸다
- **무엇을 정했나**: 에이전트가 쓰는 모든 조회 도구가 시나리오의 **관측 시각(as_of)** 이후 레코드를 코드에서 자동으로 숨긴다. 테스트로 지킨다.
- **왜 그렇게 정했나**: 정비 기록에 고장 시각의 교체 기록이 섞여 있어, 아무 조치 없이 두면 "미래 정보"가 에이전트에게 샌다.
- **대신 버린 방법**: 프롬프트로 "미래를 보지 마"라고 지시만 하기(믿을 수 없다).

### 0010 — 프로젝트의 주장과 지킬 선, 선택 실험을 못박는다
- **무엇을 정했나**: 주장("AI 가 산업 현장에 못 들어가는 병목은 모델 성능이 아니라 '어디까지 맡겨도 되는지'의 증명이 없다는 것")과 지킬 선 3개(정지는 사람, 평가 설비 격리, 데이터 비재배포), 그리고 "기본 평가가 끝난 뒤에만" 모델 2개 비교를 한다는 조건을 글로 못박았다.
- **왜 그렇게 정했나**: 구현 중 유혹(모델 바꿔 숫자 뽑기, 평가 설비 미리 보기)에 흔들리지 않기 위해.
- **대신 버린 방법**: 모델 성능 비교를 메인 결과로 올리기, 평가 중에 선을 "임시로" 완화하기.

### 0011 — 최신 연구에서 가져온 설계 결정과 사전 등록 분석
- **무엇을 정했나**: 에이전트 단계에서 지킬 네 가지(① 포맷 오류·허용 밖 행동 집계, ② A1·A2 동일 조건 실행, ③ dev 실패 시 도구 출력 형식부터 손보고 평가 전 동결, ④ 에이전트 도구는 환경의 읽기 도구 4개뿐)와, 평가 전에 미리 정하는 분석 두 가지(실패 원인 4분류, 확신 기준선 τ 는 dev 에서 정해 평가에 그대로 적용 + AUROC 함께 보고). 그리고 멀티에이전트는 지금 쓰지 않는다는 결정.
- **왜 그렇게 정했나**: 같은 방향의 최신 arXiv 사전 공개본들이 "하네스 비교의 재현성 위기는 사후 결정에서 온다"는 점을 반복해서 지적한다. 분류와 임계값을 **지금 글로 적어 두어야** 결과를 보고 숫자를 띄우는 유혹을 막는다.
- **대신 버린 방법**: 평가 뒤에 분류 기준·임계값·단계 예산을 조정하기, 자유 도구(파일·셸)를 주어 에이전트에게 "환경 밖 상태"에 접근시키기, 같은 입력에 멀티에이전트를 얹기.
