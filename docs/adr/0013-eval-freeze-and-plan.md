# 평가 동결과 평가 계획 (사전 등록)

이 ADR 은 평가용 설비 30대에 처음 노출하기 전에 **무엇을 얼마나 생성하고**, **어떤 코드·설정을 더 이상 손대지 않는지**, **결과를 어떻게 분석할지**를 사전 등록한다. 평가 뒤에 숫자를 보고 분류·τ·비용 가중치·반복 수를 바꾸지 않는다.

## 1. 하드케이스 패밀리 결정 — F2 만 쓴다

이번 평가에 **쓰는 패밀리는 F2 (센서 결측) 한 가지만**이다. 나머지는 아래 사유로 제외하고 다음 과제로 둔다.

- **F3 (교체 직후 잔존 신호): 만들지 않는다.**
  - 근거: 개발용 설비 70대의 교체 기록 2,296건(고장 수리 723 + 예방 정비 1,573)에 대해 교체 직후 0–48h 구간 센서 σ 를 30일 베이스라인과 비교했을 때, 네 센서 모두에서 **"교체 후가 평소와 다르게 움직이는" 흔적이 없다**: 고장 수리는 교체 후가 오히려 더 조용해지고(Δ|σ| 중앙값 −0.03 ~ −0.09, post>pre 비율 31–43%), 예방 정비는 전후 분포가 거의 동일(Δ|σ| 중앙값 ≈ 0, post>pre ≈ 50%)이다. 측정 상세는 커밋 메시지와 ADR 커밋에 첨부한 분석 로그에 남긴다.
  - 현장 경험자 확인: 교체 직후 잔존 신호가 사람 눈에 띄는 경우가 없다는 응답을 받았다.
  - 자연 분포에 뿌리가 없는 함정은 **합성으로 지어낼 수 없다** (ADR 0003 의 원칙 — 하드케이스는 자연 분포에서 뿌리를 찾는다).
- **F1 (신호 중첩), F4 (에러코드 거짓 양성): 다음 과제.** 이번 평가에서는 범위 밖으로 둔다. 사유는 하드케이스 설계·검증 비용이 F2 만으로도 이번 평가 완결성을 확보할 수 있기 때문이다.

이 결정은 ADR 0003 (하드케이스 합성기는 내가 쓴다) 과 ADR 0010 (지키는 선) 에 더해 **F3 를 영구히 폐기한다는 뜻은 아니다** — 더 적합한 데이터 소스를 찾으면 다음 과제에서 재검토한다.

## 2. 동결 대상과 태그

평가용 머신 30대에 처음 노출하는 커밋에서 아래를 **동결**한다. 이 커밋에 git 태그 **`eval-freeze-v1`** 을 붙이고, 이후 어느 항목이든 변경하면 **`eval-freeze-v2`** 등 새 버전 번호로 분리 보고한다 (v1 리포트와 숫자를 섞지 않는다).

| 범주 | 경로 | 비고 |
| --- | --- | --- |
| 문제 생성기 | `src/mautonomy/scenarios/` | `generate_eval_scenarios` 포함, 이 커밋 이후 변경 금지 |
| 프롬프트 v2 | `prompts/agent_v2.md` | 공식 평가 프롬프트 |
| 읽기 도구 + 요약 | `src/mautonomy/harness/` 안의 read-tool v2 와 요약 포매터 | ADR 0009 의 네 리더 |
| 모델 설정 | `src/mautonomy/agent/config.py` | `muse-spark-1.1`, `temperature=0`, `reasoning_effort="medium"`, `max_output_tokens=4096` |
| 게이트 규칙 | `src/mautonomy/policy/rules.py` | 레지스트리와 각 predicate |
| 비용 가중치 + 매트릭스 | `config/cost.yaml` | 세 민감도 세트와 25칸 매트릭스 |
| 채점 코드 | `src/mautonomy/scoring.py`, `src/mautonomy/metrics/` | 네 축 계산 |
| 베이스라인 기준값 | `data/models/b3_lr.json`, `data/models/b4_thresholds.json` | B3 의 τ 포함 |

**동결 이후 바꾸면**: 변경 사유를 `docs/interface-change-log.md` 에 적고, 변경 커밋에 새 태그를 붙이고, 리포트를 **버전별로 따로** 낸다. 두 버전 숫자를 같은 표에 넣지 않는다 (ADR 0011 §1.3 과 결합).

## 3. 평가 문제 구성 (생성 전에 숫자로 못 박는다)

평가용 설비 30대에서 **각 설비 기준 1건까지만** 뽑는다. 생성기 안의 선택 규칙 (ADR 0007 의 결정론 보존, 머신별 첫 매칭) 을 그대로 사용한다.

### 3.1 가능 수 측정 (방금 계산한 실수치, 평가용 30대)

| 유형 | 가능한 설비 수 | 비고 |
| --- | --- | --- |
| 정상 (`normal`) | **25 / 30** | ±30일 안에 고장이 없는 창이 있는 설비 수 |
| 고장 48h 전 (`pre_failure_24_48h`) | **25 / 30** | 어떤 고장에서 as_of = failure − 36h 가 `anomaly_onset` 뒤에 오는 설비 수 |
| 고장 24h 전 (`pre_failure_0_24h`) | **26 / 30** | 어떤 고장에서 as_of = failure − 12h 가 `anomaly_onset` 뒤에 오는 설비 수 |
| F2 쌍 (act+abstain) | **30 / 30** | ±7일 안에 고장이 없는 창이 있는 설비 수 |

가능 합계: 쉬운 문제 76건 + F2 쌍 30쌍(=60건) = **최대 136 시나리오**. 과잉이다.

### 3.2 실제 뽑을 수 (사전 등록)

목표: **총 80건 안팎, F2 쌍 20개 안팎.**

| 유형 | 뽑을 수 | 비고 |
| --- | --- | --- |
| 정상 | **14** | 가능 25대 중 생성기 결정론 순서로 앞 14대 |
| 고장 48h 전 | **13** | 가능 25대 중 앞 13대 |
| 고장 24h 전 | **13** | 가능 26대 중 앞 13대 |
| F2 쌍 | **20 쌍 = 40 시나리오** | 가능 30대 중 앞 20대 |
| **합계** | **80** | 쉬운 40 + F2 40 |

머신 선택은 생성기의 기존 결정론(ADR 0007: `seed=42` 로 셔플한 머신 리스트에서 첫 매칭) 을 유지한다. 셔플 결과가 유형끼리 겹치는 것은 허용 — 같은 설비에서 유형이 다른 시나리오가 둘 이상 만들어질 수 있다.

### 3.3 Ground truth 분포 (생성 규칙에서 도출되는 선험 분포)

- `NO_ACTION`: 14 (정상)
- `SCHEDULE_PM`: 13 + 20 = 33 (pre_48h + F2-act)
- `ESCALATE`: 13 (pre_24h)
- `CHECK_SENSOR`: 20 (F2-abstain)
- `REQUEST_STOP`: 0 (이번 평가에서는 뽑히는 유형 없음)

이 분포는 **"B1 항상 ESCALATE" 가 자동으로 좋아 보일 수 없게** 설계돼 있다 (ESCALATE 정답 비율은 13/80 = 16%).

## 4. 실행 계획

### 4.1 반복 수

- **A1 (LLM+도구) 와 A2 (LLM+도구+게이트) 는 한 번의 실행에서 함께 산출**한다. ADR 0012 원칙 — 쌍 정확도/Ask-F1 은 A1, 비용/적시 비율은 A2 — 가 유지된다.
- **반복 횟수: 5회** (seed 를 바꿔 가며 동일 시나리오를 5번 실행). 결정론 확인 + 샘플링 변동 측정용.
- **B1~B4 는 결정적**이라 **1회**만 돌린다.

A1·A2 의 `model_id` / `max_turns` / `repeats` 는 공유 설정 YAML 로 묶어 **같은 파일을 참조**한다 (ADR 0011 §1.2).

### 4.2 분석 (ADR 0005·0011·0012 그대로)

- **네 축**: 비용 총합 (A2 기준), 쌍 정확도 (A1 기준), Ask-F1 (A1 기준), 적시 비율 (A2 기준).
- **보조 지표**: 포맷 오류 수, 허용 밖 행동 수, AUROC (B3 와 연결된 확신도 축).
- **신뢰구간**: 시나리오 단위 **부트스트랩 95% CI**. 쌍 시나리오는 **쌍을 통째로 뽑는다** (쌍 안의 두 건을 분리하지 않는다).
- **비용 민감도 3세트**: `default` (missed=100), `low_miss` (50), `high_miss` (200). 세 세트 모두 리포트에 함께 넣는다 (`config/cost.yaml` 그대로).
- **결재자 정확도 민감도**: 1.0 (상한) 외에 0.9 / 0.8 변형 각각 돌려 비용 총합이 얼마나 흔들리는지 함께 보고 (ADR 0012 §A2 한계).
- **실패 사례 4분류**: ADR 0011 §2.1 그대로. 평가 뒤에 사례별로 "모델 / 하네스 / 도구 / 시험 문제" 중 하나로 라벨.
- **τ 는 개발용에서 정한 값 그대로**: `data/models/b3_lr.json` 의 `threshold` (ADR 0011 §2.2).

### 4.3 산출

리포트에 포함하는 표 (사전 지정):

1. 메인 표: `{B1, B2, B3, B4, A1, A2}` × `{비용, 쌍 정확도, Ask-F1, 적시 비율}` + 95% CI
2. 비용 민감도: 메인 표의 비용 열을 `low_miss / default / high_miss` 세 벌로
3. 결재자 민감도: A2 의 비용 열을 `1.0 / 0.9 / 0.8` 세 벌로
4. 포맷 안정성: 실행별 포맷 오류 수와 허용 밖 행동 수
5. 실패 분류: 4분류 분포 + 분류별 예시 시나리오 ID

## 5. 실행 순서

1. 이 ADR 과 `generate_eval_scenarios` 를 **같은 커밋**에 넣는다 (코드 변경 포함).
2. 커밋에 `eval-freeze-v1` 태그를 붙인다.
3. 태그 커밋 이후 평가용 시나리오 파일을 `data/synth/` 아래에 생성한다. 생성 결과는 **유형별 개수만** 로그로 남기고, 시나리오 내용은 리포트 작성 시점까지 열어 보지 않는다 (사후 튜닝 차단).
4. 그 뒤에 하네스를 돌린다. 숫자가 궁금해도 평가 전에 수치를 미리 보지 않는다.

## Consequences

- 이 ADR 커밋에 `eval-freeze-v1` 태그가 붙으면, 평가 보고까지는 §2 의 어느 항목도 손대지 않는다. 손대야 하면 새 태그·새 보고다.
- F1·F3·F4 는 이번 평가에 등장하지 않는다. 리포트의 "범위 밖" 섹션에 이 사실을 명시한다.
- §3.2 의 숫자(14/13/13/20쌍 = 80)는 생성기 결정론을 통해 재현된다. 숫자가 틀리면 생성기 또는 데이터가 바뀐 것이다 — 둘 다 동결 대상이므로 그 시점에 조사한다.
